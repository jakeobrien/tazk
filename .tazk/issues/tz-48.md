# Description

`tz ready` only checks an issue's own `blocked_by` links and ignores `child_of`. If an epic is `blocked_by` an open issue (for example a `role: human` ask), its children still show up in `tz ready`, so a builder agent can pick up work the epic is waiting on. Make an issue not ready, and report it as blocked, when any of its ancestors is blocked.

Today the solo-directed-agents workflow works around this by having planners copy an epic's blockers onto each child. Once `tz` handles it, that stopgap should go.

Context:
- Relevant code: `src/storage.rs` (`has_unresolved_dependencies`, `get_ready`, `get_blocked`, `get_stats`), `src/tui/model/blockers.rs`, `src/tui/data.rs`.
- Single parent is now enforced when a `child_of` link is written (`ensure_single_parent`, commit 92c8362), but merges and hand edits can still produce several parents or a cycle, so the ancestor walk must tolerate both.
- Docs that describe the stopgap: docs/workflows/solo-directed-agents.md, tazk-flow/AGENTS.md, tazk-flow/skills/tz-issue-hygiene, tz-to-tickets, tz-triage.

Repro:
1. `tz create Epic -t epic -r agent`, `tz create Ask -r human`, `tz dep add <epic> --target <ask>`.
2. `tz create Child -r agent --parent <epic>`.
3. `tz ready -r agent`. Expected: Child is absent. Actual: Child is listed.

# Design

- Inherit through `child_of` only, walking every ancestor, not just the direct parent, because epics can nest.
- An ancestor counts as blocking when it has an unresolved `blocked_by` (target open or missing) or is in `blocked` status, the same rule an issue's own links follow.
- Keep one shared rule (extend or wrap `has_unresolved_dependencies`) so `ready`, `blocked`, `stats` and the TUI can't drift apart.
- Not doing: copying epic blockers onto children (the current stopgap), because the copies go stale and children added later miss them.

# Acceptance Criteria

- An open issue is absent from `tz ready` when any ancestor reached through `child_of` has an unresolved `blocked_by` dependency (target open or missing) or has status `blocked`. Closing the ancestor's blocker makes it ready again.
- `tz blocked` lists issues blocked only through an ancestor, and for each inherited blocker names the ancestor it comes from, in both text and `--json` output. Direct blockers are reported as before.
- `tz stats` ready/blocked counts and the TUI blocker marker (`src/tui/model/blockers.rs`) follow the same rule.
- A `child_of` cycle or an issue with more than one parent (possible via merges or hand edits) terminates the walk without hanging or panicking; with several parents, a blocker on any of them blocks.
- Tests cover: blocked direct parent, blocked grandparent, ancestor blocker closed, ancestor blocker target missing, ancestor in `blocked` status, `child_of` cycle, multiple parents.
- USAGE.md documents inherited blockers for `tz ready` and `tz blocked`.
- The "copy epic blockers down" stopgap is removed: docs/workflows/solo-directed-agents.md (Concepts and Open items), tazk-flow/AGENTS.md ("Known gap"), tazk-flow/skills/tz-issue-hygiene (the `epic-blockers` check and its fix step, including scripts/report.py), tazk-flow/skills/tz-to-tickets and tazk-flow/skills/tz-triage.
- `make validate` passes.
