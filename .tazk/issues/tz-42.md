# Description

Hash ID generation changes from tz-39 §5, plus the `hash-encoding` part of §9.

Today a base36 hash can be all digits (so `x-123` could be numeric or hash), and hex hashes are all digits about 15% of the time. After this ticket, every hash suffix contains at least one letter and base36 is the only encoding. That is what lets later tickets tell the kind of an ID from its pattern alone.

# Design

- `src/hash.rs`: remove `HashEncoding::Hex`, `encode_hex` and the encoding parameter. In `generate_hash_id_with_collision_check`, treat an all-digit candidate like a collision (go on to the next nonce/length). Keep the size-scaled length (3–8). Leave the `prefix` parameter for now; tz-43 deletes it.
- `src/storage.rs`: remove `get_hash_encoding` and the `hash-encoding` lines in `write_initial_config`. If config.yaml contains `hash-encoding`, opening the store fails with the error from tz-39 §9; `tz config set hash-encoding` is rejected the same way.
- Remove `hash-encoding: base36` (and its comment block) from this repo's `.tazk/config.yaml` in the same commit, or `tz` stops working here.
- `src/bin/test_tazk.rs`: drop the hex checks (`is_hex_hash_id` etc.).

# Acceptance Criteria

- No hex code or `hash-encoding` handling is left (`rg -i 'hex|hash-encoding' src` shows only unrelated hits).
- Unit test: with an injected or brute-forced all-digit candidate, generation skips it. A test generating many IDs (e.g. 10k across lengths 3–8) never returns an all-digit suffix.
- A store whose config.yaml has `hash-encoding` fails to open with the §9 message; `tz config set hash-encoding base36` fails.
- `tz init` writes a config.yaml without `hash-encoding`.
- USAGE/README no longer mention `hash-encoding`.
- `make validate` passes.
