# Description

Needed: a planning session with the human (`tz-spec` skill) to decide per-type body formats and validation for `epic`, `spec` and `gate`, producing a spec that `tz-to-tickets` can turn into build tickets.

Why: every issue type shares one body format (Description / Design / Acceptance Criteria / Notes), but the solo-directed-agents workflow (docs/workflows/solo-directed-agents.md) uses these types with different lifecycles. Until this is decided, the workflow doc describes the formats as conventions only.

Proposed shapes (starting point, from the triage item):
- Work types (`task`, `bug`, `feature`, `chore`): unchanged.
- `epic`: Description + Acceptance Criteria (default: all children closed). No Design.
- `spec`: a free-form body (any headings, possibly long, with numbered sections that tickets refer to as `<spec-id> §N`) + Notes. The four standard sections fit poorly.
- `gate`: a placeholder blocker with no work attached, closed when an outside condition becomes true. Sections: Condition (what must happen) + How to check. `role` says who checks.

Questions to decide:
- Which `create`/`update` flags exist per type.
- Whether a spec body is opaque to section parsing, so `## Headings` inside it don't collide with the issue's sections.
- How `--field` names (`--search/--replace/--append`) map per type.
- What the TUI detail view shows per type.
- Whether validation is a hard error or a warning (`--tz-validation`), and how existing issues that don't fit are handled.

Already decided elsewhere: the role rule (forbidden on `epic`/`spec`, required on work types and `gate`) is tz-49; don't reopen it here.

Record the spec ID in this task's Notes (`tz update <id> --field notes --append "..."`), then close it (`tz close <id>`), or tell an agent the answer and ask it to do both.

# Acceptance Criteria

- A spec issue covering the questions above exists (written with the `tz-spec` skill), and its ID is recorded in this task's Notes.
