# Description

Replace free-form `tz rename` with `tz renumber` (tz-39 §7) and move `tz rename --repair` to `tz repair` (§8). `renumber` exists to fix duplicate IDs created on two branches (USAGE.md, "no merge base"), and can never produce an ID outside the canonical format.

# Design

- `tz renumber <id> [--to <suffix-or-id>] [--dry-run] [--tz-patch-code]`, with IDs parsed by the shorthand parser.
  - Numeric mode: default is the next free number; `--to` must be a free numeric ID.
  - Hash mode: default is a freshly generated hash; `--to` must be a free hash ID.
  - `--to` in the other mode's format is rejected.
  - Reuse `rename_issue`/`apply_id_mapping` for the rewrite, so triage items are covered.
- `tz repair [--dry-run]`: today's `rename --repair`, unchanged in behavior.
- Remove the `Rename` command. Keep `Storage::rename_issue` only if `renumber` uses it.
- `tests/regressions.rs`: turn the `rename` cases into `renumber` cases (including the transaction/rollback and comment-identity ones).
- USAGE: replace the rename section; add the duplicate-ID workflow to the merge driver section (on the incoming branch, before merging: `tz renumber 39 --to <n>` with `<n>` above the target branch's highest ID, commit, then merge).

# Acceptance Criteria

- `tz renumber 3` in a numeric store with max ID 7 gives `tz-8` and rewrites dependencies, parents, text mentions, comments and triage items.
- `tz renumber 3 --to 20` gives `tz-20`; `--to 5` fails if `tz-5` exists; `--to a1b` fails in numeric mode; the matching cases work in hash mode.
- `--dry-run` changes nothing and lists the changes; `--tz-patch-code` behaves as `rename` did.
- `tz repair` behaves as `tz rename --repair` did; `tz rename` is unknown to clap.
- USAGE documents `renumber`, `repair` and the duplicate-ID workflow.
- `make validate` passes.
