# Description

`tz create` and `tz triage promote` require `-r/--role` for every issue type. Under the solo-directed-agents workflow, `role` says who picks an issue up as work, and it is what routes work to agents (`tz ready -r agent`) or to the human. Epics and specs are never picked up as work: an epic is owned by the owners of its children, and a spec is produced with the human in a planning session and turned into tickets by a planning skill, never autonomously by a builder. Forcing a role onto them is misleading (an `agent` spec implies an agent may take it) and makes `tz list -r human` / `-r agent` noisier.

New rule: `role` is required exactly for the types `tz ready` can return (`task`, `bug`, `feature`, `chore`, `gate`) and forbidden on `epic` and `spec`. Apply it on `create`, `triage promote`, `update -r` / `--clear-role` and `reopen` (which today refuses any issue with no role).

Context:
- Relevant code: `src/main.rs` (`Create`, triage `Promote`, `Update`, `Reopen` handlers and arg definitions; `tz ready` already hides epics/specs unless `--type` is given), `src/storage.rs` (`create_issue`, `update_issue`, `reopen_issue`), `src/tui` (already supports `-r none` as a filter).
- Today `tz update <task> --clear-role` succeeds; under the new rule it must fail.
- Docs/workflows/solo-directed-agents.md currently describes "optional by convention" with a footnote saying `tz` still requires a role; replace that with the enforced rule.

# Design

- Role is forbidden on `epic` and `spec`, not merely optional, because role is load-bearing for routing and neither type has a single owner: an epic's owners are its children's owners, and a spec belongs to the planning session with the human. An `agent` role on a spec would wrongly suggest an agent may pick it up and turn it into tickets on its own.
- No new role value (`shared`, `none`): a value fully determined by the type is derived data, `shared` would blur `-r` filters, and a stored `none` would give two spellings of "no role". `none` exists only as a filter keyword meaning "role unset", as the TUI's `-r none` already does.
- Legacy data is tolerated: an epic/spec that already has a role still loads and accepts other updates and `tz close`; only commands that *set* a role on an epic/spec fail, pointing at `--clear-role`.
- `tz update` has no way to change an issue's type today; if one is added later it must apply the same rule.

# Acceptance Criteria

- `tz create` and `tz triage promote`: with `-r` on `epic`/`spec`, fail with an error saying these types take no role; without `-r` on `epic`/`spec`, succeed; for `task`, `bug`, `feature`, `chore`, `gate`, `-r` is still required.
- `tz update -r` on an epic/spec fails with a clear error. `tz update --clear-role` fails on work types and gates, and succeeds on epics/specs.
- `tz reopen` of an epic/spec needs no `--role` (and rejects one); work types without a role are still refused as today.
- `tz list -r none` and `tz ready -r none` match issues with no role; `-r agent`/`-r human` don't match epics/specs without a role.
- An epic/spec with a stored role (legacy) still loads, and other `tz update` changes and `tz close` on it succeed.
- This repo's existing epics and specs (tz-1..tz-6, tz-40, tz-39) have their role cleared with `tz update --clear-role`.
- Tests cover each command above, including the legacy case.
- Docs updated: USAGE.md (`role` property row, `create`, `reopen`, `list`/`ready` filters), `tz quickstart` text, docs/workflows/solo-directed-agents.md (types table, footnote, Open items, command table), tazk-flow/references/ticket-templates.md (epic/spec templates no longer pass `-r`) and any tazk-flow skill examples that pass `-r` for epics or specs.
- `make validate` passes.
