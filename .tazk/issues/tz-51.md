# Description

## 1. Problem

Every issue type has the same four body sections (Description, Design, Acceptance Criteria, Notes), and any of them can be set on any type. The solo-directed-agents workflow (docs/workflows/solo-directed-agents.md, "Body conventions by type") uses `epic`, `spec` and `gate` differently, but only by convention:

- An epic's Design has no reader. The approach belongs in the spec or the children.
- A spec is one free-form document. Design and Acceptance Criteria next to it would split it in two, and a spec is finished by being ticketed, not by meeting criteria.
- A gate with no stated condition, or no way to check it, can't be closed with confidence.

Nothing stops an agent from writing these shapes wrong. Separately, the global `--tz-validation` flag is parsed in `src/main.rs` but its value is never read.

Decided in tz-50: keep the four existing sections everywhere (same headings, JSON fields and `--field` names) and validate which ones each type may use. Gates keep the standard sections, a spec's body stays in Description, Notes is allowed on every type, an empty required section is a hard error, and `--tz-validation` is deleted.

## 2. Goals and non-goals

**Goals**
- A per-type rule for each body section: optional, required or forbidden (§3).
- Write commands enforce the rule as a hard error (§4, §5).
- Epics get a default Acceptance Criteria (§5.1).
- Issues that already break the rule still load and accept unrelated changes (§4).
- Remove `--tz-validation` (§7).

**Non-goals**
- New sections, new fields, or headings that differ by type. File headings, JSON fields, `--field` names and flags stay as they are.
- Any change to how sections are parsed. A spec's `##` headings already sit inside Description, because writing turns a column-0 `# ` in section text into `## ` (`sanitize_section_content` in `src/format.rs`).
- Checking `§N` references or the structure inside a spec.
- TUI or `tz show` changes (§6).
- Changing an issue's type (there is no command for that; if one is added, it must apply §3 too).
- A `--notes` flag on `create` / `triage promote`.
- Role rules (tz-49, done).

## 3. Section rules per type

| Type | Description | Design | Acceptance Criteria | Notes |
|------|-------------|--------|---------------------|-------|
| `task`, `bug`, `feature`, `chore` | optional | optional | optional | optional |
| `epic` | optional | forbidden | optional, defaulted on create (§5.1) | optional |
| `spec` | **required** | forbidden | forbidden | optional |
| `gate` | **required** | forbidden | **required** | optional |

- **Required:** the section must contain non-whitespace text.
- **Forbidden:** the section must be empty (whitespace only counts as empty).
- **Meaning by type:**
  - Epic: Description says what the epic delivers and how its children fit together. Acceptance Criteria is "all child issues closed" plus only criteria that can't be written as a child task.
  - Spec: Description is the whole spec, free-form, with `##` numbered sections that tickets refer to as `<spec-id> §N`. Notes holds later pointers (amendments, superseded-by).
  - Gate: Description is the condition: what has to happen, and what it blocks. Acceptance Criteria is how to check that the condition is true. `role` says who checks (tz-49).
- Work types are unchanged. The workflow's "acceptance criteria always" stays a convention for them.

## 4. When the rules are checked

- **Loading never fails on these rules.** Reading, listing, `tz show`, the TUI, `ready`, `close`, `reopen`, `claim`, labels, dependencies, comments, export and the merge driver ignore them. This matches tz-49's handling of old data.
- **A write is checked only on the sections it changes, after the change is applied:**
  - A forbidden section the command changes must end up empty.
  - A required section the command changes must end up non-empty.
  - Sections the command doesn't touch are not checked.
- **What this means for existing issues that break a rule:**
  - A spec that already has a Design can still change its title, priority, Description, Notes, and so on.
  - Its Design can be cleared (`--design ""`), but not set, appended to, or search/replaced to a non-empty result.
  - A gate whose Acceptance Criteria is already empty can be updated in other ways. It only fails when a command touches Acceptance Criteria and leaves it empty.
- **`create` and `triage promote` check every section**, because every section is new.
- If a command updates several issues (`tz update a b c ...`), each issue is checked against its own type. The first failure stops the command, with the same partial-write behavior the command has today for other errors.

## 5. Commands

Flags don't change. Each rule is applied to the resulting values.

### 5.1 `tz create`

- `--design` with non-empty text on epic, spec or gate: error.
- `--acceptance` with non-empty text on spec: error.
- Spec or gate with an empty description (no `-d` / `--description-file`, or only whitespace): error.
- Gate without non-empty `--acceptance`: error.
- Epic without `--acceptance`, or with an empty one: Acceptance Criteria is set to `- All child issues closed.`.
  - An explicit `--acceptance` replaces the default, so authors who add criteria include that line themselves.
  - The default is only set on create. Clearing it later with `update --acceptance ""` is allowed.

### 5.2 `tz triage promote`

Same rules as `create` (it builds the issue through the same path). The description defaults to the items' text, so a spec or gate created by promotion has a non-empty Description unless `-d ""` is given. A gate still needs `--acceptance`. An epic gets the default Acceptance Criteria.

### 5.3 `tz update`

Every way of changing a body section goes through §4:

- `-d/--description`, `--description-file`, `--design`, `--acceptance`, `--notes`;
- `--search/--replace` (`--replace-all`) with `--field description|design|acceptance|notes`;
- `--append` with any `--field`.

`--field title` and every non-body flag are never checked.

### 5.4 Error messages

Each message names the issue, its type and the section, and says what to do instead. Suggested wording:

- `tz-7 is an epic; epics have no Design section. Put the approach in the spec or in the child tickets.`
- `tz-7 is a spec; specs have no Design or Acceptance Criteria section. The whole spec goes in Description.`
- `tz-7 is a gate; gates have no Design section. Description says the condition, Acceptance Criteria says how to check it.`
- `A spec needs a Description: the spec itself.` / `A gate needs a Description: the condition that must become true.`
- `A gate needs Acceptance Criteria: how to check that its condition is true (--acceptance).`

For a write that is rejected only because of an existing forbidden section, the message mentions that clearing it is allowed (`--design ""`).

## 6. Display

No change. The TUI detail view, `tz show` and JSON already skip empty sections, or show them as empty, and forbidden sections are always empty on valid issues. Headings are not relabeled per type. A gate's Acceptance Criteria is still shown as "Acceptance Criteria".

## 7. Remove `--tz-validation`

Delete the global flag, the `tz_validation` field and the `ValidationMode` enum with its `FromStr` from `src/main.rs`, and the line under Options in USAGE.md. Passing the flag then becomes an ordinary unknown-argument error. Backwards compatibility is not needed (there are no stores outside this repo).

## 8. Implementation notes

- **Put the rule in one place, next to `IssueType::ensure_role_allowed` in `src/types.rs`.** For example:
  - `IssueType::section_rule(EditField) -> SectionRule { Optional, Required, Forbidden }`, using an exhaustive `match` with no wildcard arm;
  - `IssueType::ensure_section(field, text) -> Result<()>`.
- **`Section` and `EditField` both name the four body sections.** Reuse whichever is convenient. `EditField::Title` is always Optional.
- **Call sites:**
  - `Storage::build_new_issue_no_lock` (covers `create` and `triage promote`), where the epic default is also applied;
  - `apply_issue_updates` (for `update_issue`), checking only the keys present in `updates`;
  - `search_replace_issue`;
  - `append_to_issue`.
- **Check before writing**, so a rejected command leaves the file untouched.
- **The CLI's `create` handler** may also reject early, but storage is the authority (the TUI and tests call storage directly).

## 9. Existing data
