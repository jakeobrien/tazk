# Description

## 1. Problem

The issue prefix can be configured (`init --prefix`, `config set issue-prefix`,
`rename-prefix`), and IDs can be set freely (`create --id`, `rename`). It's
only useful for cross-project references and personal taste, and neither
matters for this project. It costs complexity:

- The prefix can change partway through a project.
- An ID can break the naming convention, so the code has to guess what kind of
  ID it's looking at. Examples: prefix inference from issue files or the
  directory name, the "different prefix" branches in migrate and repack, and
  the gap heuristic in `migrate --to numeric`.
- Numeric and hash IDs overlap. A base36 hash can be all digits (or 3
  characters long), so `x-123` could be either kind. Hex hashes are all digits
  about 15% of the time.
- Shorthand (`14` → `prefix-14`) works only in `tz show`, and only for numbers.

A prefix is still worth having. It namespaces an ID that could otherwise point
to anything. `tz-` is short, easy to recognize, and unlikely to collide with
anything.

## 2. Goals and non-goals

**Goals**
- Every issue ID is `tz-` plus a suffix in one of two exact, non-overlapping
  formats (§3).
- Every ID argument accepts the suffix alone (§4).
- Remove all ways to choose an ID or a prefix (§6).
- Replace the gap heuristic and prefix inference with exact pattern checks (§10).
- Migrate this repo's issues from `tazk-N` to `tz-N` (§11).

**Non-goals**
- Backwards compatibility. There are no stores outside this repo.
- Deciding whether to keep both numeric and hash modes (§13).
- Git-style unique-prefix matching of hash IDs (`tz show a1` → `tz-a1b2`).
- Changing TUI search. It already does substring matching on IDs.
- Changing triage item names (`<timestamp>-<rand>`).

## 3. Canonical ID format

```
id      = "tz-" suffix
suffix  = numeric | hash
numeric = [1-9][0-9]*                   e.g. tz-1, tz-42
hash    = [0-9a-z]*[a-z][0-9a-z]*       e.g. tz-a1b, tz-k3x9q (at least one letter)
```

- One constant for the prefix (e.g. `ID_PREFIX = "tz-"`). Nothing else spells
  it out.
- Lowercase only. No leading zeros, and no `tz-0`.
- `numeric` and `hash` cannot overlap, so the kind of an ID can always be
  determined exactly.
- An issue or comment file whose name doesn't match is invalid. It is handled
  under the `--tz-validation` mode like any other invalid issue.

## 4. Shorthand input

One shared parser (ideally a clap `value_parser`) used by every argument that
takes an issue ID:

1. Lowercase the input.
2. If it matches `id`, use it as is.
3. Otherwise, if it matches `suffix`, prepend `tz-`.
4. Otherwise, fail: `Invalid issue ID "<input>": expected tz-<n> or tz-<hash> (or just <n> / <hash>)`.

This needs no store context and never has to guess, because suffixes contain
no `-`.

It applies to every ID input, including `show`, `update`, `claim`, `block`,
`defer`, `close`, `reopen`, `children`, `dep add/remove/list/tree`,
`comments add/delete`, `create --parent/--deps`, `list --id/--parent`,
`ready --id/--parent`, `triage promote --parent/--deps`, `triage attach --to`,
and `renumber` (§7). Inside `--deps`, shorthand applies after the type is split
off: `blocked_by:12,13` → `blocked_by:tz-12,blocked_by:tz-13`.

Excluded:
- Triage item names.
- IDs in files that `tz` reads (JSONL import/sync, frontmatter dependency
  keys). Files must use the full canonical form.

Output always prints the full `tz-…` form.

## 5. Hash ID generation

- Drop hex encoding and the `hash-encoding` config key. Base36 is the only
  encoding.
- Reject all-digit candidates by moving on to the next nonce, so every hash
  suffix contains a letter. With the current length range, about 0.6–2% of
  candidates are all digits.
- Remove the `prefix` parameter threaded through `hash.rs`.
- Keep the length that scales with store size (3–8) and the collision check.

## 6. Removals

- `tz init --prefix`. Init no longer infers a prefix from the directory name or
  existing files.
- The `issue-prefix` config key and everything that reads or writes it
  (`get_prefix`, `infer_prefix`, `infer_prefix_from_issues_dir`, the special
  case in `set_config_value`).
- `tz rename-prefix` and `Storage::rename_prefix`.
- `tz rename` as free-form renaming. Replaced by `tz renumber` (§7) and
  `tz repair` (§8).
- `tz create --id`.
- `hash-encoding` (§5).

## 7. `tz renumber`

Its purpose is to fix duplicate IDs: two branches that each created `tz-39`
produce a whole-file conflict in the merge driver (USAGE.md, "no merge base").

```
tz renumber <id> [--to <suffix-or-id>] [--dry-run] [--tz-patch-code]
```

- Numeric mode: without `--to`, the issue gets the next free number (max + 1).
  With `--to`, the target must be a free numeric ID.
- Hash mode: without `--to`, it gets a freshly generated hash. With `--to`, the
  target must be a free hash ID.
- `--to` in the other mode's format is rejected. `renumber` never produces an
  ID outside §3.
- It rewrites every reference in one transaction (reuse `apply_id_mapping`):
  - dependency keys and parents in all issues,
  - ID mentions in issue text and comments,
  - **triage item text**. Today's ID rewrites (rename, migrate, repack) don't
    touch triage items. Fix that for all of them, since triage items often
    name the issue they were found during.
  - code, with `--tz-patch-code`, as now.
- Workflow, to be documented in USAGE.md: on the branch being merged in, before
  merging, run `tz renumber 39 --to <n>`, where `<n>` is above the highest ID
  on the target branch. Commit, then merge.

## 8. `tz repair`

The current `tz rename --repair` becomes its own command, `tz repair
[--dry-run]`. It removes broken references and behaves as it does today.

## 9. Config handling

- New `config.yaml` contains `tz-hash-ids` and `issue-storage-layout`, with
  their comments.
- When opening a store, if config.yaml has `issue-prefix` or `hash-encoding`,
  fail with: `config.yaml: '<key>' is no longer supported (IDs are always
  tz-…); remove it`. `tz config set` rejects both keys.

## 10. Internal simplification

- `IssueId::parse` validates against §3. ID validation no longer has to worry
  about Windows device names or invalid filename characters.
- `storage/triage.rs` currently uses `IssueId::parse` to check triage file
  names. Move the portable-filename check in `paths.rs` to its own type (e.g.
  `PortableName`), used for triage names only.
- `get_next_number`: the highest numeric suffix + 1, with no prefix filter.
- `migrate --to numeric`: classify IDs by pattern. Delete
  `find_max_numeric_id_before_gap` and the "different prefix" branch.
- `migrate --to hash` and `--repack-contiguous`: drop the prefix comparisons.
- Sharding (`sharded_relative_path`) and list ordering (`numeric_id_suffix`,
  `compare_for_list`) read the kind of ID from the pattern.

## 11. One-time migration of this repo

This is done first, with the current binary, before the §6 removals land:

1. `tz rename-prefix tz`. It renames files and rewrites dependency keys and
   mentions in issue text and comments.
2. Check triage items for `tazk-N` mentions, which `rename-prefix` doesn't
   rewrite, and fix them with `tz triage edit`. There are none at the time of
   writing.
3. Commit separately: `Migrate issue IDs tazk-N -> tz-N`. Git history keeps
   the old `tazk-N` references in commit messages. The number is unchanged, so
   they still map directly.

Removing `issue-prefix` from config.yaml happens together with §9.

## 12. Docs and tests

- README, USAGE (init flags, ID field table, rename section, merge-duplicate
  workflow), quickstart text in `main.rs`, `--help` strings, and the workflow
  doc where it shows IDs.
- Tests:
  - Drop `--prefix test` from the shell tests and update expected IDs to `tz-N`.
  - Replace the prefix/rename cases in `regressions.rs` with `renumber` cases.
  - Remove the hex checks in `src/bin/test_tazk.rs`.
  - New tests:
    - the shorthand parser (each form, case, invalid input, `--deps`),
    - hash generation never producing an all-digit suffix,
    - `renumber` in both modes, including triage text rewriting,
    - the config errors for removed keys.

## 13. Open questions

- **Numeric vs hash mode.** Migrate and repack still change IDs. Picking one
  mode would remove the migrate machinery. Hash mode avoids duplicates across
  branches. Numeric mode is friendlier to type. Out of scope here. Revisit
  after living with `renumber`.
- **Duplicate detection.** `renumber --to` relies on the user picking a free
  number on the target branch. A later improvement could be
  `--above <git-ref>`, or having the merge driver report duplicates with the
  suggested command.
