Code review: migrate --to hash reports a wrong count and can fail on collisions within the migration

Where: src/main.rs Migrate "hash" arm (~line 3364); src/storage.rs migrate_to_hash_ids (~line 2399).

Problems:
- Success message uses `changes.len() / 3`, but changes also contains the config line, dependency-update lines and triage lines, so the count is wrong. The numeric/repack arms count "Rename file:" lines instead; return the mapping length.
- New hash IDs are checked for collisions only against files on disk, not against IDs already allocated earlier in the same migration. A birthday collision makes apply_id_mapping fail with "ID mapping would overwrite issue" (safe, but a spurious failure). The follow-up "already exists ... please report this bug" check repeats what generate_hash_id already did.
- Each generate_hash_id call re-walks the issues dir to count issues (O(n^2) directory scans).

Suggested fix: pass a collision checker that also consults the in-progress mapping; compute the issue count once; report id_mapping.len().
