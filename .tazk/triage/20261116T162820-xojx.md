Code review: lock can be held by two processes at once (stale-lock takeover race)

Where: src/lock.rs, try_acquire_lock (~lines 83-110) and Drop for Lock.

Problem:
- When two processes both see a stale lock (dead PID, or an empty/invalid file older than 2s), A removes it and creates its own; B then removes A's *fresh* lock with fs::remove_file and creates its own. Both believe they hold the lock.
- Drop removes the lock file unconditionally, without checking it is still ours, so it can delete another process's lock.
- Liveness is a PID check (kill(pid, 0)). PIDs are meaningless across PID namespaces, e.g. a host process and a sandbox/container sharing the same .tazk directory; a corrupt PID such as 4294967295 becomes kill(-1, 0).

Suggested fix: use an OS advisory lock (flock / LockFileEx, e.g. the fs4 crate), or write a random token into the lock file and only take over a stale lock via atomic rename after re-reading it; only remove the lock in Drop if it still holds our token.
