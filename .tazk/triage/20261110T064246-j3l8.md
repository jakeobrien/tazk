`tz ready` should treat blockers on ancestor epics as blocking their descendants

Today `get_ready` (src/storage.rs) only checks an issue's own `blocked_by` dependencies; `child_of` is ignored. If an epic is `blocked_by` an open issue (e.g. a `role: human` ask), its child tasks still appear in `tz ready`, so a builder agent can pick up work the epic is waiting on.

Proposal: an issue is not ready if any ancestor reached through `child_of` has an unresolved `blocked_by` dependency (open or missing target). This also applies to ancestors that are in the `blocked` status. `tz blocked` should report inherited blockers and say which ancestor they come from. Watch for `child_of` cycles and multiple parents.

Context: the alternative was a hygiene skill that copies epic blockers down onto each child. That was rejected because the copies go stale (for example, a child added after propagation doesn't get them). The workflow doc (docs/workflows/solo-directed-agents.md) describes propagation as a stopgap until this is done.
